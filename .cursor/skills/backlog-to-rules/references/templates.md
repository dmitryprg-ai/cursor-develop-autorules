# Backlog-to-Rules: Templates

## Шаблон анализа backlog (Phase 1)

```markdown
## 📊 BACKLOG ANALYSIS

### 1. Группировка по файлам:
| Файл | Улучшения | Кол-во |
|------|-----------|--------|
| [protocol-*.mdc] | #X, #Y, #Z | N |
| [_base-*.mdc] | #A, #B | M |

### 2. Статистика:
- Всего улучшений в backlog: [N]
- 🔴 High priority: [N]
- 🟡 Medium priority: [N]
- 🟢 Low priority: [N]

### 3. Паттерны ошибок:
1. [Паттерн 1] — улучшения #X, #Y
2. [Паттерн 2] — улучшения #Z
```

---

## Шаблон исследования файла (Phase 2)

```markdown
## 🔍 RESEARCH: [filename.mdc]

### Текущая структура:
- Секция 1: [название]
- Секция 2: [название]
- ...

### Где добавить улучшения:
- Улучшение #X → [какая секция / новая секция N]
- Улучшение #Y → [какая секция]

### Проверка конфликтов:
- [ ] Улучшения не противоречат существующим правилам
- [ ] Формат соответствует существующему стилю
- [ ] Новые секции логически вписываются
```

---

## Шаблон плана внедрения (Phase 3)

```markdown
## 📋 ПЛАН ВНЕДРЕНИЯ

### Файл 1: [path/to/file.mdc]
- [ ] Добавить секцию X.Y: [название]
- [ ] Добавить секцию X.Z: [название]

### Файл 2: [path/to/file.mdc]
- [ ] Добавить секцию N: [название]

### Критерии успеха:
1. Все улучшения из backlog внедрены
2. Существующий контекст сохранён
3. Формат соответствует стилю файла
```

---

## Шаблон новой секции (Phase 4, формат Job Description)

```markdown
### X.Y. [Название] (из Improvement #N)

**Input:** [Что триггерит это правило]

**Output:** [Что должно быть сделано]

**Процесс:**
1. **Шаг 1:**
   ```[lang]
   [конкретный пример]
   ```

2. **Шаг 2:**
   [описание]

**Guardrails:**
- ❌ [что НЕ делать]

**Success Metric:** [как понять что правило сработало]

> **WHY:** [Реальный случай ошибки]. Потеря ~[X] минут.
```

### Чеклист качества секции:
- [ ] Есть конкретный Input (когда применять)
- [ ] Есть измеримый Output (что получить)
- [ ] Есть пример кода/команды
- [ ] Есть WHY с реальным случаем
- [ ] Есть Guardrails (если применимо)

```
