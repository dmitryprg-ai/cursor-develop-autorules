# Backlog-to-Rules: Anti-patterns

## ❌ НЕ ДЕЛАЙ

| Ошибка | Правильно |
|--------|-----------|
| Удалять существующие секции | Добавлять новые |
| Объединять несвязанные правила | Отдельная секция для каждого паттерна |
| Писать абстрактные правила | Включать конкретные примеры |
| Пропускать WHY | Каждое правило с обоснованием |
| Упрощать формулировки | Сохранять полный контекст |
| Менять нумерацию существующих секций | Добавлять в конец |
| Перезаписывать файл целиком | Точечные изменения через Edit |
| Создавать файлы с `_fixed`, `_v2` | Редактировать исходник |

---

## Типичные ошибки при внедрении

### 1. Слишком абстрактное правило
```markdown
# ❌ BAD
Всегда проверяй данные перед использованием.

# ✅ GOOD
### 3.4. Валидация Bitrix24 UF-полей
**Input:** Получены данные с UF-полями типа "Список"
**Output:** Значения замаплены из ID в текст
> **WHY:** UF-поле "Тип клиента" вернуло ID=127 вместо "Юрлицо". Потеря ~40 минут.
```

### 2. Правило без WHY
```markdown
# ❌ BAD
Не используй response.length < limit для пагинации.

# ✅ GOOD
Не используй response.length < limit для пагинации Bitrix24.
> **WHY:** Bitrix24 при start > total возвращает записи БЕЗ фильтра.
> Загружено 333K записей вместо 100. Потеря ~2 часа.
```

### 3. Потеря контекста при внедрении
```markdown
# ❌ BAD — удалил существующую секцию и заменил своей

# ✅ GOOD — добавил новую секцию после существующих,
#            сохранив нумерацию (3.4, 3.5, ...)
```

---

## Чеклист перед финализацией

- [ ] Каждое внедрённое правило содержит конкретный пример
- [ ] Каждое правило имеет WHY с реальным случаем
- [ ] Существующие секции не удалены и не изменены
- [ ] Нумерация секций корректна
- [ ] Backlog обновлён (статусы + статистика)
- [ ] Все затронутые файлы открыты и перечитаны
